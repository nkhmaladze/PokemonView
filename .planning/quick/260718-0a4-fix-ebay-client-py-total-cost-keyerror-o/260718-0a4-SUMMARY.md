# Quick Task 260718-0a4: Fix ebay_client.py total_cost() KeyError Summary

**Hardened `total_cost()` with defensive `.get()` chaining so it defaults shipping to 0.0 instead of raising `KeyError` when eBay's Browse API returns a non-empty `shippingOptions` array whose first entry lacks `shippingCost` (calculated/freight shipping without a buyer postal code, or local-pickup-only listings).**

## Accomplishments
- Added `tests/test_ebay_client.py` with a RED regression test proving `total_cost()` raised `KeyError` on a real eBay response shape (non-empty `shippingOptions`, first entry missing `shippingCost`), plus two guard tests for the already-working well-formed-shipping and no-shippingOptions-key paths.
- Hardened `scripts/ebay_client.py::total_cost()` to resolve the shipping value via `.get()` chaining (`shipping_options[0].get("shippingCost") or {}` then `.get("value")`), defaulting `shipping_cost` to `0.0` whenever the resolved value is `None`.
- Confirmed `total_cost()`'s signature and `item_price + shipping_cost` return contract are unchanged — `scripts/ingest_worker.py::upsert_listings` (its sole consumer) still passes all its tests unmodified.

## Decisions Made
- Used `(shipping_options[0].get("shippingCost") or {}).get("value")` rather than a broad `try/except KeyError` around the whole shipping computation — keeps the defensive surface narrow and scoped exactly to the shipping lookup, leaving `item_price = float(item["price"]["value"])` free to still raise loudly on genuinely malformed price data (which should not be silently swallowed).
- Left `total_cost()`'s function signature and `item_price + shipping_cost` return contract untouched, since `scripts/ingest_worker.py::upsert_listings` (line 152) depends on it as the single source of truth for `item_price`/`shipping_cost`/`total_price`.
