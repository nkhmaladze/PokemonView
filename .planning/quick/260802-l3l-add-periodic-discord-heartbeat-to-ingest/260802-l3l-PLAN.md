Logic, in order:
1. Default now to datetime.now(timezone.utc) when None.
2. Compute day_start as now.replace(hour=0, minute=0, second=0, microsecond=0) — the current UTC calendar day boundary.
3. Define the healthy-run filter as status in ["success", "partial"], the identical status set check_and_alert_staleness already treats as a good run.
4. Count healthy runs with started_at greater-than-or-equal to day_start. Return immediately unless that count is exactly 1. A count of 0 means the run that just finished was not healthy (failed or skipped_locked) so there is nothing to confirm; a count of 2 or more means today's heartbeat already went out on the first healthy run of the day, which is what keeps the 4-hourly cycle from spamming.
5. Read the webhook via os.environ.get("DISCORD_WEBHOOK_URL") and return silently when unset — bracket access is forbidden here, an unconfigured webhook must never crash the worker.
6. Count healthy runs with started_at greater-than-or-equal to now minus HEARTBEAT_LOOKBACK_HOURS for the message body, and fetch the most recent healthy run via find_one sorted by started_at descending (fall back to an empty dict so a race can never raise AttributeError).
7. Read that run's timestamp as finished_at or started_at, and normalize a naive value to UTC-aware exactly as check_and_alert_staleness does (this project's MongoClient is not tz_aware — Phase 04-04 precedent). Carry only counts and timestamps — never the webhook URL, the Mongo connection string, or eBay credentials.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker → Discord webhook | Outbound HTTPS to a third-party endpoint holding a bearer-equivalent secret in its URL |
| MongoDB → message content | Run metadata read from the DB is interpolated into an externally-visible message |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-HB-01 | Information Disclosure | send_heartbeat_if_due message body | high | mitigate | Message carries only run counts and an ISO timestamp; webhook URL, MONGODB_URI, and eBay credentials are never interpolated or logged. Asserted by test_heartbeat_fires_on_first_healthy_run_of_utc_day's negative content assertions. |
| T-HB-02 | Denial of Service | ingestion worker process | high | mitigate | A Discord outage or a missing DISCORD_WEBHOOK_URL must never crash the worker: os.environ.get + early return, and requests.RequestException caught with a 10s timeout. Asserted by test_heartbeat_missing_webhook_url_noop and test_heartbeat_post_failure_swallowed. |
| T-HB-03 | Denial of Service | Discord webhook rate limit | low | mitigate | Calendar-day debounce caps the heartbeat at one POST per 24h regardless of the 4h ingestion cadence. Asserted by test_heartbeat_not_repeated_within_same_utc_day. |
| T-HB-04 | Spoofing | false health confirmation | medium | mitigate | Only status success/partial runs are heartbeat-eligible, so a failed or lock-skipped run can never emit a "healthy" message. Asserted by test_heartbeat_silent_when_no_healthy_run_today. |
