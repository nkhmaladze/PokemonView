<task type="auto">
  <name>Task 3: Add the secret-gated Fly.io deploy job</name>
  <files>.github/workflows/ci.yml</files>
  <action>
Add a third job, `deploy`, that turns the CI workflow into CI/CD. It deploys the **backend only** — the frontend ships separately to Vercel and must not be touched here.

- `needs` set to `[backend, frontend]`. This is the "CD only after CI passes" guarantee: GitHub will not start this job unless both named jobs concluded successfully.
- `if` set to the expression `github.event_name == 'push' && github.ref == 'refs/heads/main'`. Both halves are required. The event check alone would let a branch push through; the ref check alone would still match a pull request targeting main. Together they mean no pull request — including one opened from a fork — can ever reach a production deploy.
- `runs-on: ubuntu-latest`.
- A job-level `concurrency` block with `group` `deploy-production` and `cancel-in-progress: false`, so two rapid merges queue rather than racing each other onto the same Fly app, and so an in-flight deploy is never killed halfway.
- A job-level `env` block defining `HAS_FLY_TOKEN` as the expression comparing `secrets.FLY_API_TOKEN` against an empty string. This indirection is mandatory: the `secrets` context is **not** available in a job-level `if`, but it **is** available in a job-level `env`, and the resulting value can then be read as `env.HAS_FLY_TOKEN` from any step-level `if`. Note the value is the string `'true'`/`'false'`, so compare against the quoted string. This only ever exposes a boolean about the secret's presence, never the secret itself.

Steps:
- Three deploy steps, each carrying `if: env.HAS_FLY_TOKEN == 'true'`: `actions/checkout@v4`; `superfly/flyctl-actions/setup-flyctl@master`; and a step running `flyctl deploy --remote-only` with a step-level `env` mapping `FLY_API_TOKEN` to `secrets.FLY_API_TOKEN`. Scope the token to the single step that needs it rather than the whole job. The `--remote-only` flag builds on Fly's remote builder, so the runner needs no Docker daemon. The command runs from the repo root where `fly.toml` (app `pokemonview`) and `Dockerfile` live, so no `--config` or `--app` flag is needed.
- One final step with the inverse guard `if: env.HAS_FLY_TOKEN != 'true'`, which echoes a short notice explaining that the repository secret has not been configured yet and that the deploy was intentionally bypassed. It must exit 0. This is what keeps main green before the developer adds the secret, instead of a red X on every push.

Commit and push to the branch. Verify on the resulting pull-request run that the deploy job does **not** execute — this is the security-relevant assertion, and a PR run is the correct place to prove it.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Untrusted PR code → CI runner | A contributor (or fork) can propose arbitrary code that CI then executes on a runner. |
| CI runner → Fly.io production | A runner holding `FLY_API_TOKEN` can deploy arbitrary code to the live app. |
| Third-party action → runner | Marketplace actions execute with full access to the job's environment and secrets. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-k38-01 | Elevation of Privilege | `deploy` job trigger | critical | mitigate | Deploy requires `github.event_name == 'push'` **and** `github.ref == 'refs/heads/main'`. The `pull_request` trigger is used (never `pull_request_target`), so fork PRs run without repository secrets and can never reach the deploy job. Verified empirically in Task 3. |
| T-k38-02 | Information Disclosure | `FLY_API_TOKEN` in job env | high | mitigate | The token is bound at step level only on the `flyctl deploy` step, not job-wide. Presence is tested via a derived boolean (`HAS_FLY_TOKEN`), so the secret value never reaches a conditional expression or log line. GitHub additionally masks registered secret values in logs. |
| T-k38-03 | Tampering | `superfly/flyctl-actions/setup-flyctl@master` | medium | accept | `@master` is a mutable ref: a compromised upstream would execute in a job that holds the deploy token. Accepted because the pinned-ref form was specified for this task and the action is Fly's own first-party publisher. Documented follow-up: pin to a commit SHA. |
| T-k38-04 | Elevation of Privilege | `GITHUB_TOKEN` scope | medium | mitigate | Workflow-level `permissions: contents: read`. No job requests write scope, so a compromised step cannot push commits, publish packages, or alter releases. |
| T-k38-05 | Spoofing | Fly deploy credential scope | medium | mitigate | The checkpoint instructs generating a token scoped to the single `pokemonview` app (`fly tokens create deploy -a pokemonview`) rather than an account-wide personal token, limiting blast radius. |
| T-k38-06 | Repudiation / silent failure | Test suite bypass | high | mitigate | 56 of 73 tests self-bypass when `MONGODB_URI` is absent while pytest still exits 0 — a false green that would let regressions merge. Mitigated by a real `mongo:7` service container plus an explicit assertion on the full 73-test pass count, not merely on the job's exit status. |
| T-k38-SC | Tampering | package installs (`pip install -r requirements.txt`, `npm ci`) | medium | mitigate | No new packages are introduced by this task — no package-legitimacy gate applies. `npm ci` installs strictly from the committed `package-lock.json` (fails on drift rather than resolving fresh); `requirements.txt` is fully version-pinned. |
