state it can be in with tests, make its date and price formatters directly
unit-testable so the tooltip's readability is proven rather than assumed, and

needs an assertion or a token.

whose every colour and size comes from `tokens.css`.

  <action>
Promote the three formatter helpers in `frontend/src/components/PriceHistoryChart.jsx`
from module-private functions to named exports, add the Y-axis price formatter as
a fourth, and pin their timezone so their output is deterministic.

Name them exactly `formatAxisDate`, `formatTooltipDate`, `formatAxisPrice` and
`formatTooltipValue`, and export each with the `export function` form alongside
the existing default export of the component. Keep the component's own use of
them unchanged — `XAxis` uses `formatAxisDate` as its `tickFormatter`, `YAxis`
uses `formatAxisPrice` as its `tickFormatter`, `Tooltip` uses `formatTooltipDate`
as its `labelFormatter` and `formatTooltipValue` as its `formatter`.

Add `timeZone: 'UTC'` to the options object of both `Intl.DateTimeFormat`
instances. This is a planner discretion decision, not a locked one, so record the
reasoning in a comment directly above the formatters: `price_points` timestamps
are stored and returned in UTC, the ingestion cadence that produces them is
UTC-based, and pinning the display timezone keeps a given point's tick label
identical for every viewer and makes these functions assertable in tests without
manipulating the process timezone. Note in the same comment that switching to
viewer-local time later is a display-only change confined to these two option
objects.

`formatAxisDate` keeps `{ month: 'short', day: 'numeric' }`, `formatTooltipDate`
keeps `{ month: 'short', day: 'numeric', year: 'numeric' }`, both against the
`'en-US'` locale, matching the rest of the app's fixed-locale convention. Each
takes an ISO string and constructs a `Date` from it before formatting.
`formatAxisPrice` takes a number and returns it prefixed with a dollar sign, with
no decimal places, since Y-axis ticks are round gridline values.
`formatTooltipValue` takes a number and returns a two-element array whose first
element is that value rendered with two decimal places and a leading dollar sign
and whose second element is the string `Total price` — this is the shape Recharts'
Tooltip `formatter` prop expects, where the second element becomes the series
label shown beside the value.

Create `frontend/src/components/PriceHistoryChart.test.jsx` and open it with the
formatter tests only — the rendering tests land in Task 2. Import the four
formatters by name, plus `describe`, `expect` and `it` from `vitest`. Write one
`describe` block per formatter asserting the exact output strings listed in this
task's behaviour block, including the UTC day-boundary case, so a machine in a
negative-offset timezone cannot silently change the assertion's meaning.

Do not add a date library. `Intl.DateTimeFormat` and `Number.prototype.toFixed`
cover everything here, matching the explicit convention `relativeTime.js` already
establishes.

| npm package → rendered output | Recharts controls the SVG subtree this component produces |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-04 | Tampering | `PriceHistoryChart.jsx` formatters and Recharts text rendering | low | mitigate | Every database-sourced value passes through `Intl.DateTimeFormat` or numeric formatting and is handed to Recharts as a React text child, which escapes by default; the component contains no `dangerouslySetInnerHTML` and builds no SVG markup from strings |
| T-08-06 | Denial of Service | client-side render cost of a very long unbounded series | low | accept | Recharts renders SVG per point, which is the tradeoff CLAUDE.md's alternatives table already accepted for this data volume; Task 2's five-point series and the accepted volume assumption in Plan 08-02 bound the exposure for v1.1, and D-02 records the revisit trigger |
