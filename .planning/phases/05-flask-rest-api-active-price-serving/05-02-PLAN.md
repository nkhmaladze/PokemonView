<objective>
Resolve the sample-size gap 05-CONTEXT.md's Specific Ideas section and 05-RESEARCH.md's Pitfall 3 / "Sample-Size Gap — Options for Planning" explicitly asked the planner to decide rather than default silently: add a `listing_count` field to each `price_points` document (Option A). This is a one-line, additive, backward-compatible change to `scripts/matching.py`'s `aggregate_and_write()`.

DECISION (documented, not silent): **Option A is adopted for v1.** Rationale — PITFALLS.md warns against "showing a single 'the price' number with no indication of sample size," and Option A closes that named pitfall at near-zero cost: `included` is already computed in `run_matching_once()` immediately before the `aggregate_and_write()` call, so `len(included)` needs no new query, no new data source, and no cross-collection join. It is a strict superset of "no change" in risk terms — a purely additive field, no change to any existing median computation, no change to the time-series `metaField`/`timeField` contract, and no validator on `price_points` to update (per db/init_collections.py, price_points has no `$jsonSchema`). Option B (compute from active_listings at read time) was rejected as meaningfully riskier (fragile time-window join across two deliberately-separated collections); Option C (ship without a sample-size indicator) was rejected because it consciously leaves a named UX pitfall open. This plan reopens Phase 4's `scripts/matching.py` writer intentionally and minimally, and the API side (Plans 05-04/05-05) treats a missing `listing_count` (on documents written before this change) as `null` — an explicit, distinguishable "n/a for older points" state consistent with D-01's precision-first philosophy.

Output: `scripts/matching.py` `aggregate_and_write()` writes `listing_count`; a regression test in `tests/test_matching.py` locks the behavior.
</objective>
