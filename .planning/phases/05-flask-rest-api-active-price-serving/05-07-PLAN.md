<objective>
Close the two BLOCKER-level correctness gaps recorded in 05-VERIFICATION.md (`status: failed` truths #11 and #12) and 05-REVIEW.md (CR-01, CR-02), which remain unresolved in the code shipped by Plans 05-05/05-06. This gap-closure plan does NOT replan or duplicate that work — it makes narrow, surgical fixes to the existing serving layer plus two regression tests.

- **CR-01 (exception masking):** `api/blueprints/products.py`'s over-broad `except` around `catalog_service.list_products` swallows the internal `SET_ORDER.index()` `ValueError` (raised for any unregistered `set_name` — a real server-side data-integrity bug) and misreports it as `400 {'error':'invalid_product_type'}` instead of letting it reach the global `@app.errorhandler(Exception)` as a 500. Fix: introduce a distinct `InvalidProductTypeError(ValueError)` raised ONLY by the V5 enum check inside `catalog_service.py`; narrow the route to catch that specific type; any other `ValueError` propagates untouched.
- **CR-02 (broken production CORS):** `api/app.py` passes the raw `CORS_ORIGINS` env string straight to Flask-CORS with no comma-splitting; flask-cors 6.0.5 literal-wraps the whole string as one origin, so the documented production "comma-separated list" format never matches any real `Origin` header. Fix: split `CORS_ORIGINS` on commas into a real list (keeping the literal `'*'` wildcard dev default as a single-element list) before passing to Flask-CORS's `origins=` argument.

Purpose: Phase 5's serving layer is functionally proven (56/56 tests GREEN, 10/12 must-haves) but ships two latent blockers that would bite in production — CR-01 hides real 5xx-class bugs from monitoring behind a misleading 400, and CR-02 silently blocks the deployed React SPA from reaching the API in Phase 6/7 with no server-side error trail. Both must close before Phase 6 builds further on this API.

Output: `api/services/catalog_service.py`, `api/blueprints/products.py`, `api/app.py` fixed; two new regression tests in `tests/test_api_products.py`; the full `pytest` suite GREEN.
</objective>

## API Response Contract (unchanged — this plan preserves it)

`GET /products` → 200 JSON array; `GET /products/<id>` → 200 detail object or 404 `{"error":"not_found"}`; a genuinely invalid `?product_type` → 400 `{"error":"invalid_product_type"}`; ANY other unhandled error (including an internal `SET_ORDER.index()` failure) → 500 `{"error":"internal_error"}` with no traceback. This plan makes the 500 path work for the internal-ValueError case without changing any success-path shape.
