## Typography

Inherited unchanged from `tokens.css` / `06-UI-SPEC.md` — no new sizes or weights introduced this phase.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Label | 12px | 400 (regular) | 1.5 |
| Body | 14px | 400 (regular) | 1.5 |
| Heading | 18px | 600 (semibold) | 1.2 |
| Display | 28px | 600 (semibold) | 1.2 |

Applied to this phase's new elements:

- **24h `TrendBadge` value text**: reuses the **Label** role (12px / 400 / 1.5) — identical to the existing 7d/30d badges; this is the exact same component, unmodified, called with a third `trend` prop.
- **24h trend-label caption** (the small "24h" text above the badge): reuses the **Label** role, identical to the existing `.trendLabel` class used for "7d"/"30d".
- **All-time range caption** ("All-time range (since we started tracking)"): reuses the **Label** role (12px / 400 / 1.5), same class as `.trendLabel` — this is a longer string than "24h"/"7d"/"30d" and is expected to wrap to two lines on narrow viewports; `.trendLabel` has no `white-space: nowrap` today (confirmed by reading `ProductDetailPage.module.css`), so wrapping is already supported with zero new CSS.
- **All-time range badge value text** (`$X.XX – $Y.YY`): reuses the **Label** role (12px / 400 / 1.5) — same tier as `TrendBadge`'s value text, with `tabular-nums` applied (existing utility class) so the two dollar amounts align digit-for-digit, matching every other price rendering in the app (`PriceDisplay`, `TrendBadge`).

No Body/Heading/Display-tier text is introduced by this phase — every new string is Label-tier, matching the existing trend-badge row's visual weight (deliberately secondary to the Display-tier current-price headline above it).

## Color

Inherited unchanged from `tokens.css` — **zero new color tokens introduced.** No addition to the accent's reserved-for list either (unlike Phase 8) — this phase's new elements use only the existing neutral/muted trend tokens, never accent.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0B0D12` (`--color-bg`) | Page background (unchanged) |
| Secondary (30%) | `#171A21` (`--color-surface`) / `#232833` (`--color-divider`) | Unchanged — not touched by this phase's new elements |
| Accent (10%) | `#E8A33D` (`--color-accent`) | Unchanged reserved-for list (see `06-UI-SPEC.md`/`08-UI-SPEC.md`) — **this phase adds nothing to it.** Neither the 24h badge nor the all-time range badge is accent-colored; both are semantically neutral (a recency window and a static range, not a call-to-action or a directional signal) |
| Destructive | `#D92D20` (`--color-destructive`) | Reserved, unused this phase — no destructive actions exist on this page |

**New semantic mapping decision (D-UI-01, locked):** `AllTimeRangeBadge`'s "ok" state reuses `TrendBadge`'s existing **flat** treatment — `background: var(--trend-flat)` (`#8A94A6`), `color: var(--color-bg)` — and its "insufficient_data" state reuses `TrendBadge`'s existing **muted** treatment — `color: var(--trend-insufficient)` (`#5B6472`), no background, no padding. Rationale: an all-time high/low range has no directionality (it is not "up" or "down" relative to anything), so it must never use `--trend-up`/`--trend-down`. `--trend-flat` is this codebase's only existing "neutral status: ok" semantic color, making it the correct, zero-new-token reuse rather than inventing a fifth trend color for a badge family that today has exactly four states (up/down/flat/insufficient-data). This keeps all four price-movement/range badges on the same product page visually consistent as one family of pill chips.

**Accent reserved for** (unchanged from `06-UI-SPEC.md`/`08-UI-SPEC.md` — this phase makes no addition):

- Active filter-chip background (`FilterChips`, unchanged)
- Focus ring (unchanged)
- Links — e.g. the `← Back to catalog` link (unchanged)
- Page-title (`<h1>`) bottom-border underline (unchanged)
- Price History chart's single `<Line>` stroke (Phase 8, unchanged)

## Layout Notes (phase-specific, supplementary)

- **Trend-badge row order (D-UI-03, locked):** the existing `.detail__trendSection` gains a third `.trend` child, ordered **24h, 7d, 30d** (shortest window first, matching `09-RESEARCH.md`'s own code example and the intuitive "most recent first" reading order). Do not append 24h after 30d — that would break the implied chronological left-to-right ordering.
  ```jsx
  <div className={styles.detail__trendSection}>
    <div className={styles.trend}>
      <span className={styles.trendLabel}>24h</span>
      <TrendBadge trend={product.trend_24h} />
    </div>
    <div className={styles.trend}>
      <span className={styles.trendLabel}>7d</span>
      <TrendBadge trend={product.trend_7d} />
    </div>
    <div className={styles.trend}>
      <span className={styles.trendLabel}>30d</span>
      <TrendBadge trend={product.trend_30d} />
    </div>
  </div>
  ```
- **All-time range placement (D-UI-04, locked):** a new section, structurally identical to `.trend` (label above value, `gap: var(--space-xs)`) but as its own full-width block — **not** a fourth child squeezed into `.detail__trendSection`'s flex row (see UI Considerations "overflow" backstop row above). Inserted **immediately after** `.detail__trendSection` and **before** `.detail__historySection`, preserving the page's existing top-to-bottom order: header → price → trend badges (24h/7d/30d) → **all-time range (new)** → history chart → meta.
  ```jsx
  <div className={styles.detail__allTimeSection}>
    <span className={styles.trendLabel}>All-time range (since we started tracking)</span>
    <AllTimeRangeBadge range={product.all_time_range} />
  </div>
  ```
  `.detail__allTimeSection` is a new CSS class (new rule needed in `ProductDetailPage.module.css`), but its declaration is trivial and reuses only existing tokens:
  ```css
  .detail__allTimeSection {
    display: flex;
    flex-direction: column;
    align-items: flex-start;
    gap: var(--space-xs);
  }
  ```
- **`AllTimeRangeBadge` component composition:** new file `frontend/src/components/AllTimeRangeBadge.jsx` + `AllTimeRangeBadge.module.css`, mirroring `TrendBadge.jsx`'s exact structure — branch on `!range || range.status === 'insufficient_data'` first (muted `—`, `aria-label="insufficient data"`), else render `{formatCurrency(range.low)} – {formatCurrency(range.high)}` inside a pill chip using the `--trend-flat` background (see Color > D-UI-01 above). `formatCurrency` is copy-pasted from `PriceDisplay.jsx`'s existing local helper (`typeof value === 'number' ? \`$${value.toFixed(2)}\` : '—'`) rather than imported cross-component, matching this codebase's existing convention of each display component owning its own local formatter (`TrendBadge` and `PriceDisplay` both do this today — no shared `utils/format.js` exists to import from).
- **No new loading/error state machine:** unlike Phase 8's `PriceHistoryChart` (which had its own post-mount fetch, loading state, and error state because it hit a separate `/history` endpoint), both `trend_24h` and `all_time_range` ride the same synchronous `useLoaderData()` response the page already renders today. There is no new async boundary, no new spinner/error copy to design — the only states are the ones already covered by `TrendBadge`'s and the new `AllTimeRangeBadge`'s status branching.
- **Zero-data page-level guard (success criterion 4) is a backend-plus-defensive-frontend contract, not a new UI state:** the page must never crash/blank/partially-render when `product.price_status !== 'ok'`. This is already handled structurally today — `product.trend_24h`/`product.all_time_range` render unconditionally in the trend/all-time sections regardless of `price_status` (exactly like the existing `trend_7d`/`trend_30d` do today, per `ProductDetailPage.jsx`'s existing doc comment: "the two trend fields are always-present objects and render unconditionally in both price states"). No new conditional branch is needed in `ProductDetailPage.jsx` beyond adding the two new sections — `TrendBadge`'s and `AllTimeRangeBadge`'s own internal `!trend`/`!range` guards are the last line of defense if a field were ever missing rather than explicitly insufficient-data-shaped.
