<objective>
Add the all-time high/low computation and hang it off the detail response: one
new pure service function backed by a MongoDB aggregation, and one new field
assembled on both branches of `get_product_detail`.

Purpose: the whole difficulty of this field is a single semantic distinction that
is easy to get wrong by copying the wrong neighbour. `get_trend_baseline` returns
nothing when no point falls near a target date; `get_all_time_range` has no target
date at all and only needs one point to exist. Copy the former's contract and a
brand-new product with one collected price silently reports "insufficient data"
about a price it actually has. This plan writes that distinction into the
function's own docstring and pins it with a test.

Output: `get_all_time_range`, the `all_time_range` field, and the tests that fix
both contracts in place.
</objective>

  <behavior>
    - A product with zero `price_points` documents returns `None`.
    - A product with exactly one point at total_price 29.99 returns a mapping whose `high` and `low` are both 29.99.
    - A product with points at 33.00, 42.99, 36.00 and 39.99 returns `high` 42.99 and `low` 33.00, regardless of the order they were inserted.

    - Points belonging to a different `product_id` in the same collection never contribute to either bound.

  <action>
Add `get_all_time_range` to `api/services/price_service.py`, placed after
`get_trend_baseline` and before `compute_pct_change` so the file's ordering keeps
the point-selecting functions together. It takes `db` and `product_id` and adds no
module-level import — `datetime` and `timedelta` are not needed here.

Write its docstring in this module's established style, which is unusually load-
bearing here. State what it returns: a mapping with `high` and `low`, the maximum
and minimum `total_price` ever recorded for the product. Then state the contract
distinction explicitly and by name — it returns `None` ONLY when the product has
zero `price_points` documents ever, mirroring `get_current_price`'s D-01
contract, and it is deliberately NOT a tolerance-window function like
`get_trend_baseline`: there is no target date, so there is nothing to miss, and a
product with a single stored point therefore has a legitimate range whose two
bounds are equal. Say in the docstring that a caller must not translate a
one-point result into an insufficient-data state. Add a sentence naming
`total_price` as the only field read, consistent with D-07.

Build the pipeline as two stages. First a `$match` binding `product_id` as a plain
value in an equality filter — never interpolated into an operator or into a
pipeline-stage string, identical to the already-verified filter
`get_trend_baseline` uses. Second a `$group` with `_id` of `None` and two
accumulators, `high` carrying `$max` over the `$total_price` field path and `low`
carrying `$min` over the same path. There is no `$sort` stage and there must not
be one: both extremes are order-independent, and adding a sort would imply an
ordering contract this function does not have.

Run the pipeline through `db.price_points.aggregate`, materialise the cursor into
a list, return `None` when that list is empty, and otherwise return a fresh two-
key mapping built from the first element's `high` and `low` values. Build a new
mapping rather than returning the aggregation document directly, for the same
reason `get_price_history` builds clean dicts: the raw group document is not a
shape this module's callers should depend on.

Do not compute the extremes by fetching the series and reducing it in Python.
This is the pattern `09-RESEARCH.md`'s "Don't Hand-Roll" table rules out — it
would pull an unbounded array into application memory as history accumulates,
which is the exact tradeoff `get_price_history`'s own docstring already flags as
deliberate and revisit-triggered for the one function that legitimately needs it.

Let a pymongo failure propagate. This module has no exception-handling anywhere
and this function must not introduce the first one.

Extend the module docstring's numbered contrast of the module's functions with a
fourth entry for `get_all_time_range`, one or two sentences, naming the
zero-documents-only None contract and the absence of a time window.

Append tests to `tests/test_price_service.py`, one per line of this task's
behaviour block, following the file's conventions exactly: import the function
inside each test body, use the `api_db` fixture, insert controlled documents
directly, and use a distinct seeded `product_id` per test so the tests do not
interfere. Name them descriptively — for example a zero-points case, a
single-point equal-bounds case, an out-of-order multi-point case, an all-equal-
values case, a stored-precision case and a cross-product isolation case. In the
single-point test, add an inline comment naming Pitfall 3: this is real data, not
insufficient data, and it is the case a copy of `get_trend_baseline`'s contract
would get wrong. In the out-of-order test, insert the points in a deliberately
scrambled sequence and comment that the assertion proves the result comes from
the group accumulators and not from insertion order.
